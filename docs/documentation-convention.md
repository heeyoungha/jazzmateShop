# 문서화 규칙

## 다이어그램 종류와 채택 이유

비즈니스 로직이 복잡해지면서 두 가지 관점의 문서가 필요해졌다.

1. **컴포넌트 협업 관점** — Frontend, Spring Boot, FastAPI, DB, Airflow 등 여러 컴포넌트가 각 플로우에서 어떻게 협업하는지
2. **런타임 흐름 관점** — 각 컴포넌트 내에서 어떤 클래스/레이어가 어떤 순서로 호출되고, 어떤 객체의 조회·변형이 일어나는지

### 컴포넌트 다이어그램 (`docs/component-diagram.html`)

컴포넌트 간 의존 방향과 인터페이스를 정적으로 표현한다. 어떤 컴포넌트가 어떤 플로우에 관여하는지 파악하는 데 사용한다.

### 시퀀스 다이어그램 (`docs/flow-diagram.html`)

여러 참여자 간 메시지 교환을 시간 순으로 표현한다. 이 프로젝트에서 중요한 것은 정적 클래스 구조가 아니라 런타임 호출 순서와 데이터 흐름이다.

- 비동기 FastAPI 호출, polling, 콜백처럼 타이밍이 중요한 흐름을 표현하기 적합하다.
- 어떤 컴포넌트가 어떤 DB 테이블을 조회·변형하는지, 어떤 순서로 일어나는지 명확히 드러난다.

### 다른 다이어그램을 사용하지 않는 이유

| 다이어그램 | 배제 이유 |
|---|---|
| 액티비티 다이어그램 | 단일 프로세스 내부 흐름(분기, 루프)에 적합하다. 여러 컴포넌트가 메시지를 주고받는 구조는 참여자 간 상호작용이 보이지 않아 부적합하다. |
| 클래스 다이어그램 | 정적 클래스 관계(상속, 의존)를 표현한다. 런타임 호출 순서나 데이터 흐름은 표현할 수 없다. |
| ERD | DB 테이블 구조 표현에 특화되어 있다. 컴포넌트 협업이나 런타임 흐름 표현에는 부적합하다. |
| 상태 다이어그램 | `recommendationStatus (PENDING → COMPLETED → FAILED)` 같은 단일 객체 상태 전이에는 유용하지만, 전체 플로우 표현에는 범위가 좁다. |

## 다이어그램 렌더링 도구

### 도구 비교

| 비교 항목 | Mermaid | PlantUML | D2 |
|---|---|---|---|
| 렌더링 방식 | 브라우저 내 JS (클라이언트) | 외부 공개 서버 (`plantuml.com`) 또는 로컬 JAR | 로컬 CLI → SVG 파일 생성 |
| 레이아웃 안정성 | 참여자·노드가 많아지면 텍스트·요소 겹침 발생 | 레이아웃 엔진이 서버 사이드라 결과가 일정함 | TALA 레이아웃 엔진으로 복잡한 다이어그램도 안정적 |
| 외부 서버 의존 | 없음 | 공개 서버 사용 시 다이어그램 소스 외부 전송 | 없음 (로컬 CLI) |
| HTML 삽입 | JS 라이브러리 로드 | pako 압축 → base64 → `img src` | 빌드 시 SVG 생성 후 인라인 삽입 |
| 생태계 | GitHub/Notion/GitLab 기본 내장, 가장 널리 쓰임 | 오랜 레거시, IDE 플러그인 성숙 | 비교적 최신 도구, 채택 증가 중 |
| 로컬 미리보기 | VS Code 플러그인 | VS Code / IntelliJ 플러그인 | VS Code 플러그인, CLI |

### 현재 채택: PlantUML (공개 서버 방식)

`flow-diagram.html`은 `<pre class="plantuml">` 태그에 소스를 작성하면, pako로 압축·인코딩 후 `plantuml.com/plantuml/svg/`로 렌더링한다. 별도 빌드 단계 없이 정적 HTML 파일 하나로 동작한다.

**보안 트레이드오프 (인지된 결정)** — 다이어그램 소스가 공개 외부 서버로 전송된다. 실무 환경에서는 허용되지 않는 결정이다. 이 프로젝트는 GitHub에 공개된 개인 포트폴리오이므로 감수할 수 있는 트레이드오프로 판단해 채택했다.

### 향후 전환 고려: D2

외부 서버 의존 없이 레이아웃 안정성을 확보하려면 D2가 적합하다. 로컬 CLI로 SVG를 생성해 HTML에 인라인 삽입하면 보안 문제와 레이아웃 문제를 모두 해결할 수 있다. 단, 다이어그램 소스를 수정할 때마다 CLI로 SVG를 재생성하는 빌드 단계가 필요하다는 점이 현재 방식 대비 불편하다.

## 갱신 규칙

이 프로젝트는 SDD 원칙("구현보다 문서를 먼저 수정")을 따른다. 다이어그램도 동일하게 적용한다.

| 트리거 | 갱신 대상 | 타이밍 |
|---|---|---|
| 새 API 엔드포인트 또는 플로우 추가 | `flow-diagram.html` — 해당 플로우 시퀀스 다이어그램 추가 | 구현 전 설계 단계 |
| 컴포넌트 간 의존 방향 변경 (예: 새 서비스 도입, 모듈 분리) | `component-diagram.html` | 구현 전 설계 단계 |
| 기존 플로우의 호출 순서·DB 조회 변경 | `flow-diagram.html` — 해당 플로우 시퀀스 다이어그램 수정 | 구현 전 설계 단계 |
| 다이어그램 종류·렌더링 도구 변경 | 이 문서 (`documentation-convention.md`) | 변경 적용 시 즉시 |
