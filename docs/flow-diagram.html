플로우 05 — AllAboutJazz 데이터 파이프라인

Airflow 3-DAG 파이프라인이 AllAboutJazz 리뷰를 수집하고, OpenAI Batch API로 요약/임베딩을 생성한 뒤 PostgreSQL에 저장한다.

DAG 1 — URL 수집 · 크롤링 · GPT Batch 제출

DAG 1 시퀀스
@startuml
skinparam backgroundColor #FAFAFA
skinparam sequenceArrowThickness 1.5
skinparam participantFontSize 13

participant "Airflow\nDAG 1" as DAG1
participant "PostgreSQL" as DB
participant "AllAboutJazz\n(Playwright)" as AAJ
participant "OpenAI\nBatch API" as OAI
participant "Slack" as SL
participant "DAG 2" as DAG2

DAG1 -> DAG1 : 수동 트리거

== check_pending_batch ==
DAG1 -> DB : 1) SELECT crawl_jobs\nJOIN pipeline_batches\n(status IN ['pending','failed']\n+ attempt_count < 3\n+ batch_num ASC LIMIT 1)
DB --> DAG1 : batch_id, batch_num / null
DAG1 -> DB : 2) SELECT crawl_jobs\nJOIN allthatjazz_raw\n(같은 batch, raw 없는 job만 필터)
DB --> DAG1 : job_ids[] / null

alt 미완료 batch 존재 (resume)
  DAG1 -> DAG1 : XCom에 batch_id · job_ids push
else 신규 batch
  == create_batch ==
  DAG1 -> DB : SELECT pipeline_batches\nWHERE airflow_dag_run_id = {run_id}
  alt 이미 존재 (멱등성)
    DB --> DAG1 : batch_num, batch_id (재사용)
  else 신규
    DAG1 -> DB : INSERT pipeline_batches\n(airflow_dag_run_id)
    DB --> DAG1 : batch_num, batch_id
  end

  == collect_and_register_urls ==
  DAG1 -> DAG1 : Variable.get("current_start_page")
  DAG1 -> AAJ : URL 목록 수집 (Playwright)
  AAJ --> DAG1 : review URL[]
  DAG1 -> DB : SELECT crawl_targets\n(기존 URL 중복 체크)
  DAG1 -> DAG1 : 신규 URL만 추출

  alt 신규 URL 0건
    DAG1 -> DAG1 : AirflowSkipException\n(이후 task 스킵)
  else 신규 URL 존재
    DAG1 -> DB : INSERT crawl_targets\n(신규 URL만)
    DAG1 -> DB : INSERT crawl_jobs\n(crawl_target_id, status=pending)
  end

  == update_page_variable ==
  DAG1 -> DAG1 : Variable.set("current_start_page")\n(end_page + 1, 순환: 2000 → 1)
end

== crawl_details ==
DAG1 -> DB : SELECT crawl_jobs\nJOIN crawl_targets, allthatjazz_raw\n(status IN ['pending','failed'])
DB --> DAG1 : pending_jobs[]

loop 각 job 처리
  alt has_raw (이미 크롤링됨)
    DAG1 -> DB : UPDATE crawl_jobs\n(status → success, 보정)
  else 크롤링 필요
    DAG1 -> DB : UPDATE crawl_jobs\n(status → running)
    DAG1 -> AAJ : 리뷰 상세 크롤링 (Playwright)
    AAJ --> DAG1 : review_data, original_html
    DAG1 -> DAG1 : validate + date 파싱
    DAG1 -> DB : INSERT allthatjazz_raw\n(crawl_job_id, 파싱된 리뷰 필드들)
    DAG1 -> DB : UPDATE crawl_jobs\n(status → success | failed)
  end
end

alt 성공률 < 80%
  DAG1 -> SL : 알림 전송
  DAG1 -> DAG1 : Task 실패
else 성공률 >= 80%
  == submit_gpt_batch ==

  alt 재시도 (try_number > 1) + XCom에 openai_batch_id 존재
    DAG1 -> DAG1 : XCom pull(openai_batch_result)
    DAG1 -> DB : INSERT processing_jobs\n(DB 저장만 재시도)
  else 신규 실행
    DAG1 -> DB : SELECT crawl_jobs\n(batch_id, status='success')
    DB --> DAG1 : crawl_job_ids[]
    DAG1 -> DB : SELECT allthatjazz_raw\n(crawl_job_id IN ids)
    DB --> DAG1 : reviews[]

    alt 리뷰 0건
      DAG1 -> DAG1 : AirflowSkipException
    else 리뷰 존재
      DAG1 -> OAI : file upload
      OAI --> DAG1 : file_id
      DAG1 -> OAI : batch create
      OAI --> DAG1 : openai_batch_id
      DAG1 -> DAG1 : XCom push(openai_batch_result)\n(DB 저장 전, 중복 방지)
      DAG1 -> DB : INSERT processing_jobs\n(stage=gpt, openai_batch_id)
    end
  end

  DAG1 -> DAG2 : TriggerDagRunOperator\n{batch_id, openai_batch_id}
end
@enduml

check_pending_batch

방향테이블필드
1) READcrawl_jobs JOIN pipeline_batchesbatch_id, status, attempt_count, batch_num (pending/failed + attempt < 3, batch_num ASC LIMIT 1)
2) READcrawl_jobs JOIN allthatjazz_rawid (같은 batch 내 raw 데이터 없는 job만 필터링)
XCom push—pending_batch → batch_num, batch_id, job_ids, pending_count (job_ids 길이, DB 컬럼 아님)

2단계 조회:
1) crawl_jobs에서 pending/failed 상태의 가장 오래된 batch를 찾고,
2) 해당 batch 내 allthatjazz_raw에 데이터가 없는 job만 필터링한다.

왜 2단계인가? PostgREST(Supabase 클라이언트)에서 FK JOIN된 컬럼의 null 필터링을 지원하지 않아 Python 후처리가 필요하다. 한 쿼리로 합치면 여러 batch가 실패로 쌓였을 때 불필요한 데이터까지 전부 조회하게 되므로, 1단계에서 LIMIT 1로 batch를 먼저 특정해 조회 범위를 줄인다.

결과에 따라 resume_pending_batch 또는 create_batch로 분기한다. pending_count는 DB 컬럼이 아니라 필터링된 job_ids 길이를 계산한 임시값이다.

참고: pipeline_batches에는 status 컬럼이 없고 completed_at/cancelled_at 타임스탬프로 상태를 판단한다. crawl_jobs.status는 pending · running · success · failed · skipped 5가지 값을 가진다.

create_batch

방향테이블필드
1) READpipeline_batchesid, batch_num (WHERE airflow_dag_run_id = run_id, 멱등성 체크)
2) INSERT (없을 때만)pipeline_batchesairflow_dag_run_id (batch_num은 DB 자동생성)

반환값: { batch_num, batch_id } → XCom으로 다음 task에 전달.

멱등성 보장: Airflow task 재시도 시 동일한 airflow_dag_run_id로 기존 batch를 재사용한다. pipeline_batches에는 status 컬럼이 없고, completed_at/cancelled_at 타임스탬프로 상태를 판단한다.

collect_and_register_urls

방향테이블필드
READAirflow Variablecurrent_start_page
READ (외부)AllAboutJazz리뷰 URL 목록 (Playwright)
1) READcrawl_targetsurl (조건 없음 — 테이블에 존재하는 URL 전부 제외, 중복 등록 방지)
2) INSERT (신규만)crawl_targetsurl
3) INSERTcrawl_jobsbatch_id, crawl_target_id, status='pending'
INSERT (실패시)error_historystage, batch_id, error_type, error_message, http_status_code, error_details

반환값: { batch_num, batch_id, url_count, end_page }

URL 중복 방지: register_crawl_jobs에서 crawl_targets 테이블에 이미 존재하는 URL을 제외하고 신규 URL만 INSERT한다.

스킵 동작: 신규 URL이 0건이면 current_start_page Variable을 업데이트하고 AirflowSkipException을 발생시켜 이후 task를 스킵한다.

데이터 변형 흐름

1. Playwright 크롤러

  • 메서드: PlaywrightJazzCrawler.collect_links_in_single_tab()
  • 입력: start_page: int, end_page: int
  • 후처리: dict.fromkeys()로 중복 제거 (task 내 인라인)
// 출력: List[str] — 절대 URL (페이지별 리뷰 링크) [ "https://www.allaboutjazz.com/album-review-1", "https://www.allaboutjazz.com/album-review-2", ... ]

2. SupabaseService

  • 메서드: SupabaseService.register_crawl_jobs()
  • 입력: urls: List[str] (위 결과), batch_id: str
  • 내부 처리: SELECT로 멱등성 체크 → 신규만 INSERT crawl_targets → 응답의 id로 INSERT crawl_jobs
// INSERT crawl_targets [{ "url": "https://www.allaboutjazz.com/album-review-2" }, ...] // INSERT crawl_jobs (crawl_targets INSERT 응답의 id 사용) [{ "batch_id": "uuid-...", "crawl_target_id": "uuid-...", // crawl_targets.id "status": "pending" }, ...] // 반환: int (등록된 job 수)

update_page_variable

방향대상필드
READXCom (collect_and_register_urls)end_page
WRITEAirflow Variablecurrent_start_page → end_page + 1 (2001 이상이면 1로 순환)

collect_and_register_urls의 반환값에서 end_page를 받아 다음 실행의 시작 페이지를 갱신한다.

스킵 경로와의 차이: 신규 URL 0건으로 스킵될 때는 collect_and_register_urls 내부에서 직접 Variable을 업데이트하고 AirflowSkipException을 발생시키므로 이 task는 실행되지 않는다. 즉, 성공 경로에서만 실행된다.

crawl_details

방향테이블필드
1) READcrawl_jobs JOIN crawl_targets, allthatjazz_rawid, status, attempt_count, crawl_target_id, url, has_raw (status IN [pending, failed])
2) UPDATEcrawl_jobsstatus → 'running', started_at, updated_at, attempt_count
READ (외부)AllAboutJazz리뷰 상세 HTML (Playwright)
WRITE (외부)S3원본 HTML 저장 → s3_original_html_path
3) INSERTallthatjazz_rawcrawl_job_id, title, published_date, published_date_raw, crawled_at, is_fully_complete, s3_original_html_path 등 파싱된 리뷰 필드
4) UPDATEcrawl_jobsstatus → 'success' | 'failed', completed_at, updated_at
INSERT (실패시)error_historystage, batch_id, crawl_job_id, error_type, error_message, error_details, s3_original_html_path

성공률 < 80% 이면 Slack 알림 후 Task 실패. 반환값: { batch_num, batch_id, success_count, failed_count, duration }

상태 전이: pending/failed → running → success | failed. 각 전이마다 updated_at과 해당 타임스탬프(started_at/completed_at)를 갱신한다.

has_raw 보정: allthatjazz_raw에 이미 데이터가 있으면(has_raw=true) 크롤링을 건너뛰고 status를 success로 보정한다. 이전 실행에서 크롤링은 성공했지만 상태 업데이트가 실패한 경우를 처리한다.
